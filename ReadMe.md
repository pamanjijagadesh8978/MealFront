# RedMealGPT-mini: FastAPI + Streamlit

A TDEE/BMI-driven profile builder (Streamlit) that calls an LLM-powered
meal-generation FastAPI backend.

## Files

- **`goals.py`** — single source of truth for reference data: activity
  levels, allergies, diseases, cuisines, digestive triggers, goal
  recommendations, and the calorie/macro-split rules. This module was
  imported by every other file but wasn't itself uploaded, so it's
  reconstructed here — see the docstring at the top for the assumptions made
  (protein g/kg ranges, carb/fat %, calorie-adjustment amounts). Adjust the
  numbers freely if your product has different clinical guidance.
- **`utils.py`** — TDEE (Mifflin-St Jeor), ideal/adjusted body weight,
  protein/carb/fat macro split, and meal-calorie breakdown math. Unchanged
  from what you uploaded.
- **`user_profile.py`** — `build_profile()` turns raw form input into a full
  profile (age, BMI, goal, calories, macros, per-meal breakdown) and
  `format_profile()` renders a readable summary. One fix: `MEAL_GUIDANCE` used
  `evening_snack` while every other meal-slot list in the app uses
  `afternoon_snack` — renamed for consistency.
- **`app.py`** — the Streamlit frontend (built from your `app2.py`, which was
  the more complete of the two uploaded versions). Builds the profile with
  `build_profile()`, then calls the FastAPI endpoints below. Fixed:
  `CUISINE_OPTIONS` / `DIGESTIVE_ISSUE_FOOD_OPTIONS` are now sourced from
  `goals.py` instead of a separately hand-typed list, so every option a user
  can select matches a real key in the backend's exclusion-lookup
  dictionaries (a mismatched string there would silently produce no
  exclusions for that item).
- **`meal_gpt_core.py`** — your original `RedMealGPTmini.py` prompt/LLM logic,
  refactored into two callable service functions
  (`generate_recommended_foods`, `generate_meal_plan_with_ingredients`).
  Now imports `ALLERGIES`, `DIGESTIVE_AGGRAVATING_FOODS`, `VERIFIED_DISEASES`,
  and `CUISINE_EATING_PATTERNS` from `goals.py` rather than keeping its own
  copies, so the profile form and the prompt-builder can't drift apart.
- **`fastapi_app.py`** — exposes `POST /api/v1/food-recommendations` and
  `POST /api/v1/meal-plan-with-ingredients`, matching the paths/payload shape
  `app.py` already calls.
- `requirements.txt`, `.env.example`

## How the pieces fit together

```
Streamlit (app.py)
  -> build_profile() [user_profile.py + utils.py + goals.py]   (no LLM call)
  -> POST /api/v1/food-recommendations       [fastapi_app.py -> meal_gpt_core.py]  (LLM call)
  -> POST /api/v1/meal-plan-with-ingredients [fastapi_app.py -> meal_gpt_core.py]  (LLM calls)
```

The profile form computes calories/macros/meal-distribution locally (BMI,
TDEE, Mifflin-St Jeor, protein g/kg, etc. — all deterministic math, no LLM).
Only food recommendations and the meal plan + ingredients are generated by
the LLM, via the FastAPI backend.

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env
# edit .env with your Azure OpenAI-compatible credentials
```

## Run

Terminal 1 (backend):
```bash
uvicorn fastapi_app:app --reload --port 8000
```

Terminal 2 (frontend):
```bash
streamlit run app.py
```

Set the backend URL in the Streamlit sidebar (⚙️ API Settings) if it isn't
running on `http://localhost:8000`.

## Endpoints

1. **`POST /api/v1/food-recommendations`**
   Input: `{"profile": {...}}`
   Saves `recommended_foods_<timestamp>.json` under
   `data/<username>_<last4-of-user_id>/` and returns
   `{"user_id", "username", "timestamp", "file_path", "food_recommendations", "token_usage"}`.

2. **`POST /api/v1/meal-plan-with-ingredients`**
   Input: `{"profile": {...}, "food_recommendations": {...}}`
   Saves `meal_plan_<timestamp>.json` and
   `meal_plan_with_ingredients_<timestamp>.json`, returns
   `{"user_id", "username", "timestamp", "meal_plan_path", "meal_plan_with_ingredients_path", "meal_plan_with_ingredients", "meal_plan", "token_usage"}`.

The 4 per-day ingredient-expansion calls in Stage 2 run in parallel via
`ThreadPoolExecutor`, replacing the original script's LangGraph
`StateGraph`/`Send` orchestration — same behavior, no graph dependency needed
for a plain request/response API.
